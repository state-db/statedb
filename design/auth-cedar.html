How authorization works,
and how Cedar makes the call.

Every protected request in state-db ends at one yes-or-no question. This page builds up the answer from scratch — what Cedar is, the four things it looks at, and exactly how one real request becomes an allow or a deny.

01 · the mental model

Cedar is a yes/no engine

It does not store anything and it does not know your database. You hand it a question, your policies, and the facts relevant to that question. It returns Allow or Deny. That's the whole job.

the question
principal action resource + context
→
Cedar engine
evaluates your policies
against the request's entities
→
ALLOW → run the handler
DENY → 403 / 404
The two rules that decide everything

Default deny. If no policy says yes, the answer is no. A permit rule grants access; a forbid rule withholds it — and a single forbid beats every permit. That ordering is how we build break-glass admins and guardrails that even admins can't cross.

02 · the question

Four words: may who do what to which thing?

Cedar phrases every request the same way. Here is what each part is in state-db when the Pulumi CLI calls in.

principal — the caller

The User behind the credential — console session, CLI login token, or service-account token — carrying the Role they hold in this resource's org (more on that in §06).

action — the operation

One verb, named IAM-style: stack:Read, stack:Delete, stack:Lock …

resource — the target

A Stack / Project / Org, each named like an ARN: statedb:stack:acme/web/prod.

context — the rest

Time, IP, request metadata. Available to policies via when clauses; state-db doesn't use it yet.

03 · the facts

Entities — the only facts Cedar sees

This is the piece people miss. Cedar can't query your DB, so on every request you hand it a small bag of entities — typed objects, each with optional attributes and parents. Parents form hierarchies; the keyword in walks them.

// the caller — a User whose parent is the role she holds here
User::"7f3c…e21"
  parents:    [ Role::"viewer" ]

// the target — a Stack that descends from its Project, then its Org
Stack::"statedb:stack:acme/web/prod"
  attributes: { id: "statedb:stack:acme/web/prod" }   // for resource.id like "…"
  parents:    [ Project::"statedb:project:acme/web" ]

Type::"id"

Every entity has a type (User, Stack) and a stable id. That's Cedar's spelling; the id is the part you read.

attributes

Key/value facts on the entity. We put the resource name in id so policies can pattern-match it.

parents → in

a in B is true when B is a or an ancestor of a. One keyword, three hierarchies — next.

The bundle of entities handed to Cedar for one request is called the slice. Assembling the right slice is most of what the authorizer does — you'll watch it happen in §07.

Why names are strict. Resource ids join names with /, so a slash inside a name could collide two stacks onto one entity id — and one stack's grants would apply to the other. Hence the grammar: names are [A-Za-z0-9._-]{1,100}, enforced on create/rename (NameGrammar) and backstopped by a DB CHECK.

04 · the leverage

Three little ladders keep policies tiny

Because in climbs parents, one short rule covers many cases. These are the three hierarchies fed into every slice.

Roles — higher is-a lower

So in Role::"guest" admits every human role, while in Role::"viewer" excludes guests — a bare guest matches no static policy and sees only what policy_grants rows give them (the share-template guard keys on Role::"guest"). in Role::"member" admits member + owner. admin and service (CI machine identities) stand alone — the service grant set (service.cedar: read, decrypt, lock, encrypt) evolves without ever reshaping human permissions.

So a grant on the Org (resource in ?org) reaches every stack beneath it.

05 · the rules

Reading a policy, token by token

A policy is one permit or forbid with a head (principal / action / resource) and an optional when. Here's the rule that lets members write — annotated.

// member.cedar — the "PowerUserAccess" managed policy
permit(
  principal in Role::"member",
  action    in Action::"stack:WriteAccess",
  resource
);
permit( … )
If everything in the head matches this request, vote Allow.
principal in Role::"member"
The caller is a member — or an owner, since owner inherits member (ladder #1).
action in Action::"stack:WriteAccess"
Any action in the write bundle: Create, Lock, Delete, Encrypt (ladder #2).
resource
No constraint. Tenancy is already handled — the role on the principal is the one held in this resource's org (§06).

The flip side: an explicit Deny

A forbid reads the same way but votes the other direction — and it wins over any permit. This guardrail blocks deleting a production stack, for anyone:

// guardrails.cedar — DenyDeleteProtectedStacks
forbid(
  principal,
  action == Action::"stack:Delete",
  resource
)
when { resource.id like "statedb:stack:*/prod" };
forbid( … )
If this matches, vote Deny — and override every permit, including the admin's.
principal
Unconstrained: applies to everyone.
action == Action::"stack:Delete"
Exactly the delete action — note == (this one), not in (a group).
when { resource.id like "…/prod" }
Only when the resource's name ends in /prod — pattern-matched IAM-style.
06 · the one big idea

Global roles, resolved per request

Notice the policies have no org clause. That's deliberate, and it's the keystone of the whole design. A user is one global identity who can hold a different role in each org. So we never ask "what is her role?" — we ask "what role does she hold in this resource's org?"

◆ same User ◆

per request
Org "globex"
owner

why this is the keystone

One component — PrincipalRoleResolver — answers (credential scope, resourceOrg) → role and attaches that role to the Cedar principal. Now every policy is pure role logic with no tenancy clause to repeat, and multi-org "just works." No role in that org (and not an admin)? The request stops before Cedar even runs — stack routes as a 404, org routes as a uniform 403. Either way, existence never leaks across the boundary.

The credential draws the boundary

Before the resolver looks anything up, the credential's scope says which orgs it may be used against at all. Three ways in, two scopes:

console session

all current memberships

Browser SSO (OIDC). Role looked up live in org_members for the resource's org, on every request.

CLI login token

all current memberships

Minted by pulumi login after an explicit approval page; 24h TTL. Same live lookup as the console — revoke a membership and the token loses that org instantly.

service-account token

single org

A CI machine identity: a user row under the reserved local:service issuer holding service in one org — worth nothing anywhere else. Minted/revoked by org owners; dies with the membership (the auth query joins org_members).

07 · the payoff

One request, traced to its verdict

Now watch it all run. Every protected handler funnels through the same pipeline; a denied request never even opens a database transaction.

Authenticate

The token header is hashed (SHA-256; plaintext is never stored) and one query authenticates the actor and builds the credential scope — for a single-org token it joins org_members, so a revoked membership stops authenticating, not just authorizing.

Cedar checks every policy against the request:

✗ReadOnlyAccessviewer ✓ — but Delete isn't in ReadOnlyAccess

✗DenyDeleteProtectedStacksnot a /prod stack — doesn't fire either

Same machinery, the other rule: forbid beats permit

Now an owner deletes the prod stack. A permit does match this time — but the guardrail fires, and forbid wins.

✓StackFullAccessowner ✓ · Delete ∈ stack:* ✓ — votes Allow
✦DenyDeleteProtectedStacksresource.id ends in /prod ✓ — votes Deny
Deny One forbid overrides the permit — not even an owner (or admin) can delete prod.→ 403
the second lane: update-token

During pulumi up, the checkpoint/event writes don't re-run this pipeline. Cedar ran once, at lock acquire (stack:Lock); the CLI gets back a short-lived lease token that is the proof of that decision. Lease-scoped routes authenticate it instead (Authorization: update-token) — hashed at rest, valid for exactly one stack + update, path mismatch → 409. One matcher (LeaseRouteMatcher) decides which lane a route belongs to, so the two filters can never disagree.

08 · the four kinds of policy

Where rules come from

All four end up in one validated policy set, assembled at startup and rebuilt when a grant changes (a bad grant can never take auth down — the last good set is kept).

A

Static role policies

Pure RBAC, checked into git: AdministratorAccess, StackFullAccess, PowerUserAccess, ReadOnlyAccess. One role → one capability.

B

Deny guardrails

Org-wide forbid rules that override everything — like the protected-prod rule. The state-db take on an AWS SCP.

C

Managed (per-user)

StackWriteAccess — attach a capability to one user across one org. A reusable template + a DB row, no redeploy.

D

Resource-based (per-stack)

Stack{Read,Write}ResourcePolicy — share exactly one stack with one user. The state-db take on an S3 bucket policy.

C and D are Cedar templates with ?principal / ?resource slots; a policy_grants row binds the slots to real entities. So per-user grants are data, not deploys.

09 · if you know AWS

The IAM mental map

state-db borrows IAM's authoring model while keeping Cedar as the engine. If a construct feels familiar, it's meant to.

state-dbAWS IAM equivalent
Role policies (Administrator/PowerUser/ReadOnly…)≈AWS managed policies
forbid guardrail≈SCP / permission-boundary Deny
action groups (stack:*, stack:WriteAccess)≈action wildcards "stack:*"
statedb:stack:acme/web/prod + resource.id like≈ARNs + Resource matching
StackWriteAccess template + grant≈identity-based managed policy attachment
Stack…ResourcePolicy template + grant≈resource-based policy (bucket policy)

The one deliberate departure from IAM: a non-member sees 404 on stack routes (org routes answer a uniform 403 whether the org exists or not) — either way, tenants can't enumerate each other across the org boundary.
