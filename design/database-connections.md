# Database connections

In the production profile, the datasource asks `DatabaseCredentialsProvider` for
credentials each time the pool opens a physical JDBC connection. The provider
returns either a configured password or a freshly signed RDS IAM authentication
token. `STATEDB_JDBC_URL` supplies the database URL and `STATEDB_DB_USER` the
role name in both modes. Development and test profiles use Quarkus Dev Services
instead.

The application role owns the objects Flyway creates. It needs `CONNECT` on the
database and `USAGE` and `CREATE` on the `public` schema, but it does not need
to own the database or hold administrator privileges.

## Password mode

`STATEDB_DB_AUTHENTICATION=password` is the default and also requires
`STATEDB_DB_PASSWORD`. The provider hands the configured credentials to the pool
unchanged.

## RDS IAM mode

`STATEDB_DB_AUTHENTICATION=aws-iam` also requires `STATEDB_DB_HOST` and
`STATEDB_DB_REGION`; `STATEDB_DB_PORT` defaults to 5432.
`RdsIamAuthenticationTokenGenerator` signs an RDS `connect` token valid for 15
minutes using the ECS task role's temporary credentials.

`EcsTaskCredentialsProvider` reads those credentials from the ECS metadata
endpoint at `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`. It reuses cached
credentials only while they remain valid for longer than the token lifetime, so
a token never outlives the credentials that signed it. It does not implement
the AWS SDK's general credential chain, so IAM mode works only on ECS.

A token is generated only when the pool opens a physical connection, never for a
pool checkout, transaction, or query. RDS checks the token only when a
connection is established, so an open session survives the token's expiry. The
production pool still retires connections after ten minutes, which bounds
connection age and exercises credential refresh regularly. That interval is an
operational choice; the token lifetime does not require it.

IAM authentication does not replace TLS or PostgreSQL privileges. The AWS
template connects with `sslmode=verify-full` against the RDS certificate bundle
included in the container image.

The signer and credential reader live in
[app/database](../modules/app/src/main/java/app/statedb/app/database/).
Their tests compare signatures with vectors generated by the AWS SDK for Java
and cover query encoding, temporary credentials, refresh, and configuration
errors. They do not replace a check against a live RDS instance.

## AWS bootstrap

An IAM permission to connect does not create a PostgreSQL role or grant SQL
privileges, so the [CloudFormation template](../deploy/aws/cloudformation.yaml)
runs a separate bootstrap step. RDS keeps the master password in a managed
secret. Before the application service starts, a Lambda-backed custom resource
runs a one-off Fargate task that reads that secret and, in one transaction under
an advisory lock, creates the `statedb` login role if it is absent and grants it
`rds_iam`, `CONNECT` and `TEMPORARY` on the database, and `USAGE` and `CREATE` on
`public`. The SQL is idempotent because a CloudFormation rollback cannot undo a
committed transaction.

Bootstrap runs as its own task because ECS task roles apply to a whole task.
Folding it into the application task would give the long-running service the
master credential. Application tasks can neither read the master secret nor
connect as the master user; their task role allows `rds-db:connect` only as
`statedb`. Flyway then creates the schema through the application datasource.

The [AWS deployment guide](../deploy/aws/README.md) covers installation.
