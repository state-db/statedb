# state-db Console — UX Design & Screen Inventory

Input artifact for console build sessions. Each screen spec in §5 is a self-contained
work unit: hand one section (plus §1–§4 for context) to a build session and it has
everything it needs — route, layout, shadcn building blocks, data contract, states,
and acceptance criteria.

Companion docs: [`architecture.md`](architecture.md) (console API surface, auth,
SPA build), [`db-schema.md`](db-schema.md) (what data exists to render).

---

## 1. Product framing

state-db is a **state management console**, not a Pulumi Cloud clone. The CLI owns
all mutation of infrastructure; the console exists so humans can answer questions
the CLI answers badly:

- *What is deployed right now?* — browse resources in a stack without running
  `pulumi stack export` and reading JSON.
- *What happened, when, and who did it?* — update history, event logs, diffs.
- *Why is my `pulumi up` blocked?* — see and (as admin) break stack locks.
- *How do I authenticate?* — self-serve CLI tokens, admin-managed service tokens.
- *Is the deployment healthy?* — providers, users, orgs, compaction, license usage.

### Personas

| Persona | Frequency | Jobs |
|---|---|---|
| **IaC engineer** (primary) | daily | Find a stack, inspect resources/outputs, read an update's log via the CLI permalink, mint a CLI token when the 24h one expires |
| **Operator / site admin** | weekly | Configure OIDC, manage orgs/users/memberships, mint CI service tokens, force-unlock a stuck stack, watch compaction, manage license |
| **Auditor / teammate** | occasional | Read-only: who changed what, when; stack outputs for consumption |

### Design principles

1. **Read-first.** Every mutation in the UI is operational (tokens, unlock, delete
   empty stack, admin CRUD) — never infrastructure mutation. No "deploy" buttons.
2. **Dense, data-first.** Tables over cards wherever the data is enumerable. This
   is a tool for engineers; optimize for scanning, not marketing polish.
3. **Stock shadcn.** Every screen composes from stock shadcn/ui components (see §4).
   No bespoke component library. Custom CSS only for the resource tree indent and
   the log viewer line rendering.
4. **The permalink contract is sacred.** Routes the Pulumi CLI generates must
   resolve (§2). Everything else is ours to design.
5. **Single-org is the 99% case.** Multi-org is supported but never in the way:
   org switcher collapses to a static label when the user belongs to one org.
6. **Secrets stay secret.** Ciphertext values in checkpoints render as a `secret`
   badge. The console never decrypts. No reveal affordance in Wave 2.

## 2. URL map

The URL space is split in two: the **root namespace is a compatibility shim**
owned by the Pulumi CLI's link-generation code, and **all product screens live
under `/console/...`**, a namespace we own outright. Root-level CLI URLs are
pattern-matched redirects into `/console`; nothing renders at root.

Why the prefix: the CLI builds links against the console host root, so root
must accommodate `/{org}/...` shapes forever. If our own screens also lived at
root, every new fixed route (`/admin`, `/settings`, …) would be a potential
collision with an existing org name, forcing an ever-growing reserved-name
blocklist. With the prefix, the collision surface is *frozen* at the handful of
names below, the console can add routes freely, and the redirect layer is the
stable seam if console routes ever reorganize — old permalinks keep resolving.

### 2.1 Routes fixed by the Pulumi CLI (compatibility surface)

Source: `pulumi/pkg/backend/httpstate/client/console.go` and
`backend.go` (`getPermalink`, `cloudConsoleStackPath`, `loginWithBrowser`).
The CLI *replaces* the backend URL's path when building console links, so all of
these arrive at the **console root**, not under `/pulumi`.

| Route | Generated by | Handling |
|---|---|---|
| `/{org}/{project}/{stack}` | `pulumi console`, stack listings | redirect → `/console/{org}/{project}/{stack}` |
| `/{org}/{project}/{stack}/updates/{version}` | permalink after `up` / `refresh` / `destroy` | redirect → `/console/.../updates/{version}` (`version` = integer `stack_updates.version`) |
| `/{org}/{project}/{stack}/previews/{updateID}` | permalink after `pulumi preview` | redirect → `/console/.../previews/{updateID}` (`updateID` = `stack_updates.id` UUID) |
| `/cli-login?cliSessionPort=&cliSessionNonce=&…` | browser-based `pulumi login` | Already implemented server-side (`CliLoginResource`); not an SPA route |
| `/welcome/cli` | end of browser login | Already implemented server-side; not an SPA route |
| `/account/tokens` | access-token hint printed by older CLIs | redirect → `/console/account/tokens` |
| `/user/settings/tokens` | access-token hint printed by newer CLIs (observed in the wild; both variants must resolve) | redirect → `/console/account/tokens` |
| `/{user}` | `b.URL()` (rare; e.g. some whoami paths) | 1-segment fallthrough: redirect → `/console/{seg}` (org view; target 404s if no such org) |

**Permalink caveat to surface in onboarding UX:** for a custom backend the CLI
prints permalinks only when `PULUMI_CONSOLE_DOMAIN=<console-host>` is set (or the
backend host is `localhost:8080`, which maps to `localhost:3000`). The setup /
empty-state screens must show this export line alongside `pulumi login`.

### 2.2 Root redirect rules

Implemented as SPA compat routes (the existing SPA-fallback filter already
serves `index.html` for non-`/api`/`/pulumi` paths; TanStack Router matches the
shapes below in `beforeLoad` and issues a client-side `redirect` with
`replace: true`). No new server code.

| Root pattern | Condition | Redirect target |
|---|---|---|
| `/` | — | `/console` |
| `/account/tokens` | exact | `/console/account/tokens` |
| `/user/settings/tokens` | exact | `/console/account/tokens` |
| `/{a}/{b}/{c}` | 3 segments | `/console/{a}/{b}/{c}` |
| `/{a}/{b}/{c}/updates/{n}` | `n` integer | `/console/{a}/{b}/{c}/updates/{n}` |
| `/{a}/{b}/{c}/previews/{id}` | `id` UUID | `/console/{a}/{b}/{c}/previews/{id}` |
| `/{seg}` | 1 segment, not a fixed name | `/console/{seg}` |
| anything else | | SPA 404 page |

Existence validation happens on the redirect *target* (the screen 404s with its
empty state), keeping the redirect layer logic-free.

**Frozen reserved names.** Org (and user) names must still be blocked from a
small set — but the set is closed, tied only to protocol and infrastructure
prefixes, and never grows with the screen inventory:
`api`, `pulumi`, `tofu`, `console`, `assets`, `cli-login`, `welcome`,
`account`, `user`, `favicon.ico`. (Server-side validation at org creation — backend
task. An org named `console` or `api` would break its own permalinks under any
scheme, so these are inherent, not incidental.)

### 2.3 Console routes (product namespace)

```
/console                                        Stacks (home) — cross-org flat list
/console/login                                  Sign-in (provider chooser + break-glass)
/console/{org}                                  Org-scoped stacks home (grouped by project)
/console/{org}/{project}                        Project view: stacks in project
/console/{org}/{project}/{stack}                Stack detail (tabs: resources | outputs | activity | settings)
/console/{org}/{project}/{stack}/updates/{version}    Run detail (update/refresh/destroy)
/console/{org}/{project}/{stack}/previews/{updateID}  Run detail (preview variant)
/console/account/tokens                         Personal access tokens + CLI token mint
/console/admin                                  Admin index (redirect to first section)
/console/admin/providers                        OIDC providers
/console/admin/orgs                             Organizations (tenant lifecycle)
/console/admin/orgs/{org}                       Members & guest grants (owner-or-admin)
/console/admin/users                            Users
/console/admin/tokens                           Service-account tokens
/console/admin/operations                       Active locks + compaction queue health
```

Router: TanStack Router, code-based route tree (extend the existing
`modules/web/src/router.ts`). All `/console` routes except `/console/login`
live under the authenticated `AppShell` layout route which loads `GET /api/user`
and redirects to login on 401 (pattern already established in
`routes/home.tsx`). The root compat routes from §2.2 sit outside the shell —
they never render UI, only redirect.

## 3. Information architecture & app shell

### 3.1 Shell layout

Replace the current top-bar-only `AppShell` with a shadcn **Sidebar** layout
(sidebar-07 pattern: collapsible to icons) + header bar:

```
┌──────────┬──────────────────────────────────────────────────────┐
│ ⌗ state-db│  Breadcrumb: acme / networking / prod        [👤 ▾] │
│           ├──────────────────────────────────────────────────────┤
│ ▸ Stacks  │                                                      │
│ ▸ Tokens  │                 <route outlet>                       │
│           │                                                      │
│ Admin     │                                                      │
│ ▸ Providers                                                      │
│ ▸ Orgs    │                                                      │
│ ▸ Users   │                                                      │
│ ▸ Service │                                                      │
│   tokens  │                                                      │
│ ▸ Operations                                                     │
│           │                                                      │
│ [org ▾]   │  ← org switcher pinned to sidebar footer             │
└──────────┴──────────────────────────────────────────────────────┘
```

- **Nav groups:** `Stacks` and `Tokens` (→ `/console/account/tokens`) for everyone;
  a `Manage` group appears for site admins and org owners. Site admins see
  Providers, Orgs, Users, Service tokens, and Operations; owners see
  only Service tokens. `/console/admin/orgs/{org}` remains the other
  owner-accessible management route, reached contextually from the org.
- **Org switcher** (sidebar footer, shadcn `DropdownMenu` on a `SidebarMenuButton`):
  lists `user.organizations`. Selecting an org filters the Stacks screen and
  breadcrumb root. When the user has exactly one org, render a static label.
  Persist selection in localStorage; deep links to `/console/{org}/...` override it.
  **Site admins get an all-orgs switcher**: when `user.siteAdmin`, the list is
  sourced from `GET /api/admin/orgs` (all tenants), not `user.organizations` — a
  site admin's power comes from the `STATEDB_ADMIN_SUBJECTS` allow-list, not from
  `org_members` rows, so the switcher must not be membership-limited when they
  browse or manage another tenant. Selecting an org navigates to its scoped stacks
  home (`/console/{org}`), whose owner/admin-only "Manage members" action opens
  `/console/admin/orgs/{org}`. The single-org static-label collapse applies to
  non-admins only.
- **User menu** (header right, `Avatar` + `DropdownMenu`): email, role badges,
  theme toggle (light/dark, `next-themes` pattern), Sign out (`/api/auth/logout`).
- **Breadcrumb** (shadcn `Breadcrumb`): mirrors the URL hierarchy; each segment
  links to its screen.
- **Toasts**: `sonner` mounted once in the shell. All mutation feedback goes
  through toasts; errors that block a screen use inline `Alert` instead.

### 3.2 Cross-cutting conventions

Every build session must follow these; they are part of every screen's acceptance
criteria implicitly.

| Concern | Convention |
|---|---|
| Data fetching | TanStack Query. Query keys namespaced by route params, e.g. `['stack', org, project, stack]`. Mutations invalidate the narrowest key. |
| Loading | shadcn `Skeleton` rows matching the final layout (table skeletons = 5 ghost rows). Never a full-page spinner. |
| Empty states | Dedicated empty component per screen (icon + one-line explanation + primary action). Copy specified per screen below. |
| Errors | Inline `Alert` variant=destructive with retry button; 401 anywhere → redirect to login; 404 on a ref → screen-level "not found" empty state. |
| Timestamps | Relative ("3h ago") with absolute ISO in a `Tooltip`. One shared `<Timestamp>` util component. |
| Identifiers | URNs, UUIDs, token IDs render in `font-mono text-xs` with a copy-on-click button (`Button` variant=ghost size=icon + toast "Copied"). |
| Status badges | One shared `<StatusBadge>` mapping: `succeeded`→green outline, `failed`→destructive, `in-progress`→blue + pulse dot, `cancelled`→muted. Update kinds (`update` `preview` `refresh` `destroy` `import` `rename`) get neutral `Badge` variant=secondary. |
| Secrets | Any checkpoint value carrying the Pulumi secret sig (`4dabf18193072939515e22adb298388d`) renders as `Badge` variant=outline with a lock icon reading `secret`. Never render ciphertext. |
| Destructive actions | Always `AlertDialog` with explicit consequence copy; type-to-confirm (stack name) for stack delete. |
| Polling | Screens showing an `in-progress` update poll their queries at 3s (`refetchInterval` conditional on status). No SSE in Wave 2. |
| Pagination | Cursor/offset per API; UI uses shadcn `Pagination` under tables, 50 rows/page default. |
| Responsive | Desktop-first. Sidebar collapses to icon rail < 1024px; tables allow horizontal scroll on small screens. No dedicated mobile layouts in Wave 2. |

## 4. shadcn component kit

Stock components used across the console — install once as a foundation task:

`sidebar`, `breadcrumb`, `button`, `card`, `table`, `tabs`, `badge`, `dialog`,
`alert-dialog`, `sheet`, `dropdown-menu`, `avatar`, `input`, `label`, `select`,
`switch`, `form`, `tooltip`, `skeleton`, `alert`, `sonner`, `separator`,
`scroll-area`, `collapsible`, `pagination`, `command`, `popover`, `checkbox`,
`textarea`, `progress`, `toggle-group`, `hover-card`.

Tables with sorting/filtering use the shadcn **Data Table** pattern
(`@tanstack/react-table` + `table` primitives) — build one shared `DataTable`
wrapper in the foundation task and reuse it everywhere.

Theme: stock shadcn `neutral` base, default radius, light+dark. Accent usage is
reserved for status color (green/red/blue badges) — the chrome stays neutral.
Monospace stack (`font-mono`) for all technical identifiers and the log viewer.

### S0 · Foundation (shell + shared components)

**Not a screen — the prerequisite build unit.**

Scope:
- Install the shadcn kit (§4); configure dark mode.
- `AppShell` v2 per §3.1 (sidebar, breadcrumb, org switcher, user menu).
- Authenticated layout route: loads `GET /api/user` once, exposes it via context;
  401 → `/console/login`. Admin nav group gated on `siteAdmin`.
- Root compatibility redirect routes per §2.2 (pattern match → `redirect` with
  `replace: true`; no UI).
- Shared components: `DataTable` (sortable/filterable/paginated wrapper),
  `StatusBadge`, `KindBadge`, `Timestamp`, `CopyableId`, `SecretBadge`,
  `EmptyState`, `ErrorAlert`.
- Route tree stubs for every route in §2.3 rendering placeholder `EmptyState`s,
  so later sessions only fill screens in.

API: `GET /api/user` (exists).

Acceptance: signing in shows the shell with working nav, org switcher, theme
toggle, sign-out; every route renders a placeholder; `siteAdmin=false` hides
Admin; each §2.2 root pattern (incl. `/account/tokens` and a synthetic
`/{org}/{project}/{stack}/updates/3`) lands on the matching `/console` route.

### S1 · Sign-in — `/console/login`

**Purpose.** Provider chooser for OIDC login; break-glass form when the server
reports no enabled provider.

**Layout.** Centered `Card` (max-w-sm) on a plain background: product wordmark,
"Sign in to state-db", then one `Button` (variant=outline, full-width, provider
name) per enabled provider → navigates to `/api/auth/login/{provider}` (full page
navigation, not fetch). Single provider: still show the button (no auto-redirect —
auto-redirect loops are hostile when the IdP errors). A `?returnTo=` param is
honored post-login.

**Break-glass variant.** When the providers list is empty **and** the server
reports `breakGlass: true`, render a password `Input` whose submit fetch-POSTs
urlencoded credentials to `/api/auth/local` (Quarkus form auth in SPA mode:
200 sets the encrypted session cookie, 401 on any failure), with an `Alert`
explaining it only works from localhost unless remote access was explicitly
allowed at deploy time. A 401 shows an inline destructive `Alert` (wrong
password / gate closed — indistinguishable by design); success navigates to
`returnTo`. When providers are empty and `breakGlass: false`, render an
empty state ("Configure an OIDC provider, or set
`STATEDB_LOCAL_GLASS_PASSWORD_HASH`") — never a form that cannot succeed.

**Data.** `GET /api/auth/providers` → `{ providers: [{ name, displayName }],
breakGlass: boolean }` (public, unauthenticated; implemented).
`breakGlass` is true iff the password hash is configured and zero providers are
enabled — the loopback gate is still enforced server-side on the POST.

**States.** Loading: skeleton buttons. IdP error return (query param from
callback): destructive `Alert` "Sign-in failed at {provider}". Empty providers →
break-glass variant or the no-sign-in-methods empty state per `breakGlass`.

**Acceptance.** With 2 providers configured, both buttons render and complete the
OIDC round-trip; with none + hash configured, break-glass form renders and a
correct password lands on `/console` as the bootstrap admin; wrong password shows
the inline alert; with neither, the empty state renders; failed IdP round-trip
shows the alert rather than a blank page.

### S2 · Stacks (home) — `/console`

**Purpose.** The landing screen: every stack the user can see, scoped by the org
switcher, optimized for "find my stack in one keystroke".

**Layout.**

```
Stacks                                    [ Search stacks…        ] 
──────────────────────────────────────────────────────────────────
Project ▾ | Stack     | Last update            | Resources | Status
──────────────────────────────────────────────────────────────────
networking                                                    (group header row)
          | prod      | ✓ update · 2h ago · v14 |   38      | 🔒 locked
          | staging   | ✗ update · 1d ago · v9  |   12      |
payments  |           |                         |           |
          | prod      | ✓ refresh · 3d ago · v41|  204      | ● updating
```

- `DataTable` grouped by project (group header rows), sorted project → stack.
  Columns: stack name (link), last update (StatusBadge + kind + relative time +
  version), resource count, state indicators (lock icon with `Tooltip`
  "Locked by {locked_by} since {t}"; pulsing dot for in-progress update).
- Search `Input` filters client-side across org/project/stack names (fetch is
  one page of all workspaces; server pagination only when >500 rows — note for
  API design).
- Org switcher (shell) constrains the list; "All organizations" option when
  multi-org.
- Row click → `/console/{org}/{project}/{stack}`.

**Data.** `GET /api/workspaces` → `[{ id, kind, org, project, stack, version,
resourceCount, lastUpdate: { kind, status, startedAt, version } | null,
lock: { lockedBy, lockedAt } | null }]`. Endpoint exists as a stub; the DTO above
is the contract to implement (slice 28 + lock/lastUpdate enrichment). `kind` is
`pulumi` today; render a small `Badge` only when a second kind exists (Tofu later).

**States.** Empty (no stacks anywhere) → S16 onboarding. Empty search → "No
stacks match". Loading → table skeleton.

**Acceptance.** Stacks from two projects group correctly; search narrows; a
locked stack shows the lock tooltip; an in-progress update shows the pulse and
the row polls to completion.

### S3 · Org & Project views — `/console/{org}`, `/console/{org}/{project}`

**Purpose.** Resolve the hierarchy's intermediate URLs; lightweight scoped
versions of S2. Tier 2 — until built, these routes redirect to `/console` with
the org switcher/search preset.

**Layout.** Same `DataTable` as S2 filtered to the org (grouped by project) or
project (flat). Header adds context: org/project name, counts
(`N projects · M stacks`), created date. No tabs: `/console/{org}` remains the
org-scoped stacks home. Owners of that org and site admins see a "Manage members"
action linking to S17; other roles see only the stack browsing controls. The
**project** route has no membership controls (membership is org-scoped).

**Data.** Same endpoint as S2 with `?org=` / `?project=` filters. 404 → screen
EmptyState "No such project" with link home.

**Acceptance.** Deep-linking `/console/{org}` lands on the grouped org stack
list, including a useful empty state when it has zero stacks; only an owner of
that org or a site admin sees "Manage members." Deep-linking
`/console/{org}/{project}` lands on the filtered list; unknown names 404 cleanly.

### S4 · Stack detail — Resources tab — `/console/{org}/{project}/{stack}`

**Purpose.** The crown-jewel screen: what is deployed right now. Answers "what
resources exist, how are they related, what are their properties" without
`pulumi stack export`.

**Layout.**

```
acme / networking / prod                                  🔒 by ci@… · 12m
v14 · 38 resources · last update ✓ 2h ago · pulumi 3.242.0     [Export ⬇]
┌ Tabs: [Resources] [Outputs] [Activity] [Settings] ─────────────────────┐
│ [ Filter by type or name… ]                  [☰ Flat | 🌲 Tree]        │
│ ─────────────────────────────────────────────────────────────────────  │
│ Type                          | Name          | Provider  | Modified   │
│ aws:s3/bucket:Bucket          | site-assets   | aws       | 2h ago     │
│ aws:cloudfront:Distribution   | cdn           | aws       | 9d ago     │
│ ▸ awsx:ec2:Vpc  (component, 12 children)      | awsx      | 30d ago    │
└─────────────────────────────────────────────────────────────────────────┘
                                    → row click opens Sheet (right, 480px):
                                      URN (copyable) · type · parent · provider
                                      [Inputs] [Outputs] [Dependencies] sections
                                      key/value table, secrets masked,
                                      nested objects in <Collapsible> JSON view
```

- **Header block** (shared across all stack tabs): breadcrumb-derived title, lock
  banner (`Alert` when locked: who/since; admin sees "Force unlock" → S14
  behavior inline), stat line (version, resource count, last update badge,
  pulumi version), `Export` button downloading the reconstructed checkpoint JSON.
- **Table** (`DataTable`): columns type, name (from URN tail), provider, custom
  vs component, created/modified (from resource `created`/`modified` fields when
  present). Type filter input matches substring on type + name.
- **Tree toggle** (`ToggleGroup`): tree mode nests by `parent` URN using
  `Collapsible` rows with indent; flat mode is the plain sorted table. Default
  flat (predictable for search); persist choice in localStorage.
- **Detail `Sheet`**: full resource record — inputs/outputs as two-column rows;
  scalar values inline, objects/arrays as collapsible pretty-printed JSON
  (`ScrollArea`); secret values → `SecretBadge`. Dependencies section lists
  `dependencies` / `parent` / `provider` URNs as links that re-open the sheet on
  that resource.

**Data.** `GET /api/pulumi/stacks/{org}/{project}/{stack}` → `{ org, project,
name, version, tags, lock, lastUpdate, resourceCount, resources: [ResourceV3…] }`
(slice 29; head exists via `StackHeadFinder`, resources via `StackAssembler`).
Export button: same payload's deployment, or a dedicated
`GET .../export` console proxy — **decide in API session; UI just needs a URL**.
Resource lists can be large: fetch once, filter client-side; if >2000 resources,
virtualize rows (note for build session; `@tanstack/react-virtual`).

**States.** Empty (0 resources): "No resources — run `pulumi up` on this stack".
Stack not found → 404 EmptyState. Update in progress: banner `Alert` (blue)
"Update v15 in progress — resources shown are from v14" + link to the live run
(S8); poll head every 3s.

**Acceptance.** A stack with nested component resources renders both modes;
secrets never show ciphertext; sheet dependency links navigate between
resources; export downloads valid deployment JSON.

### S5 · Stack detail — Outputs tab

**Purpose.** Stack outputs are the stack's public API — teammates come here to
grab an endpoint or bucket name.

**Layout.** Within the S4 tab frame: two-column `Table` (key | value). Scalars
copyable inline; objects/arrays as collapsible JSON; secret outputs →
`SecretBadge` (no reveal). An `Alert` (muted) notes "Secret outputs can be read
with `pulumi stack output --show-secrets`".

**Data.** Outputs come from the synthetic `pulumi:pulumi:Stack` resource's
`outputs` in the same S4 payload — no extra endpoint.

**States.** Empty: "This stack has no outputs. Export values with
`pulumi.export(...)`."

**Acceptance.** String/number/object/secret outputs each render per convention;
copy button copies the raw value (objects: JSON).

### S6 · Stack detail — Activity tab

**Purpose.** Update history — the audit log for one stack.

**Layout.** Within the S4 tab frame: `DataTable`, newest first, paginated:

| col | content |
|---|---|
| Version | `v14` (mono); previews show `—` |
| Kind | KindBadge (`update`/`preview`/`refresh`/`destroy`/…) |
| Status | StatusBadge |
| Message | update message/description, truncated w/ tooltip |
| Changes | compact op summary from the summary event: `+3 ~1 -2` (green/amber/red mono) |
| Duration | `ended_at - started_at` |
| Started | Timestamp |

Row click → S8 (`/updates/{version}` for versioned runs, `/previews/{id}` for

persist a summary column — **API session decision**). Slice 29's
`UpdateHistoryFinder`.

**States.** Empty: "No updates yet". In-progress top row polls.

**Acceptance.** Mixed history (previews + updates + a failure) renders with
correct badges and links; pagination boundaries work; filters combine.

### S7 · Stack detail — Settings tab

**Purpose.** Stack metadata + the operational danger zone. Tier 2.

**Layout.** Stacked `Card`s within the S4 tab frame:

### S8 · Run detail — `.../updates/{version}` and `.../previews/{updateID}`

**Purpose.** THE permalink target — where `pulumi up`'s "View in Browser" lands
mid-run (via the §2.2 root redirect). Must be excellent for both a live in-progress run and a historical one.
One screen, two resolvers (by version int / by update UUID); previews render
identically minus the version chip.

**Layout.**

```
acme / networking / prod  ·  Update v14        ✓ succeeded · 2m 14s
"deploy cdn invalidation fix"    started 2h ago · pulumi 3.242.0
─────────────────────────────────────────────────────────────────
+3 created   ~1 updated   -0 deleted   38 unchanged        (chips)
┌ Tabs: [Log] [Changes] [Configuration] ────────────────────────┐
│ Log: terminal-style viewer (dark bg, mono, preserved order)   │
│   [All | Diagnostics only]  [⬇ jump to bottom]  (auto-follow  │
│    while in-progress; diagnostics colored by severity)        │
│ Changes: table of resource ops: op badge (create/update/      │
│    delete/replace/read) | type | name; row → Sheet with the   │
│    event's old/new property detail when present               │
│ Configuration: k/v table of update config (secrets masked) +  │
│    options (parallel, dryRun…) + environment metadata         │
└────────────────────────────────────────────────────────────────┘
```

- **Live mode**: while `status=in-progress`, poll events (3s, continuation by
  sequence) and append to the log; header StatusBadge pulses; on terminal status,
  stop polling and toast "Update finished: {status}".
- **Log tab**: renders `update_events` in sequence order — `stdout` events as
  raw lines (preserve whitespace, `ScrollArea`, monospem); `diagnostic` events
  colored by severity (error→red, warning→amber). Filter toggle to diagnostics
  only. This is a styled list, not a terminal emulator — no ANSI handling beyond
  stripping escape codes (util in foundation if needed).
- **Changes tab**: derived from `resourcePre`/`resOutputs`/`resOpFailed` events:
  op → colored badge (create green, update amber, delete red, replace purple,
  same hidden by default). For a standalone refresh, Pulumi's terminal
  `same`/`update`/`delete` result supersedes its initial `refresh` event. For
  `preview --refresh` and `up --refresh`, `refresh` describes a preliminary
  phase; a later `same` must not relabel that visit. No-diff refresh visits are
  activity, not evidence of a state change. Actual changes render first.
  Unchanged resources and no-diff refresh activity are summarized by count and
  available behind one `Checkbox`, so they cannot bury a meaningful change.
  A completed refresh with no actual changes shows "No drift detected"; a live
  run reports that more results may arrive. A meaningful operation without a
  displayable property diff remains visible and explains that Pulumi supplied
  the operation without property-level details.
- **Configuration tab**: from `stack_updates.config/options/metadata` — config
  keys with `secret: true` masked.

**Data.**
- `GET /api/pulumi/stacks/{ref}/updates/{version}` and
  `GET /api/pulumi/stacks/{ref}/previews/{updateId}` → update row incl. config/
  options/metadata (**API gap**: slice 29 defines list + events; the two
  single-run resolvers must be added — version→row and uuid→row).
- `GET /api/pulumi/stacks/{ref}/updates/{id}/events?after={seq}` (slice 29,
  paginated by sequence — the `after` cursor is what live-follow needs).

**States.** Not found → EmptyState "No update v{n} on this stack". In-progress →
live mode. Event retention expired (events vacuumed after 30d) → Log tab shows
"Event log expired per retention policy" `Alert` while Changes/Configuration
still render from `stack_updates`.

**Acceptance.** Opening the CLI-printed permalink during `pulumi up` shows the
log growing to completion; a preview permalink resolves by UUID; a 40-day-old
update still shows config + summary with the retention notice.

### S11 · Admin — Organizations — `/console/admin/orgs`

**Acceptance.** A created org appears immediately in a site admin's org switcher

### S12 · Admin — Users — `/console/admin/users`

**Purpose.** Support/audit view of every identity in the `users` table — humans
who have signed in, plus the machine identities minted as service accounts.
Service accounts *are* `users` rows (reserved issuer `local:service`), so they
are present by default, not absent; this is also the only cross-org inventory of
them, since S13 is org-scoped.

**Layout.** `DataTable`: user (Avatar + name + email, with an inline `admin`
`Badge` when the row is a site admin) | identity (`iss` short + `sub` mono,
copyable — what an admin pastes into `STATEDB_ADMIN_SUBJECTS`) | orgs (badges

`ToggleGroup` (Humans / Service accounts / All, default **Humans**) segments on
the DTO's `principalType` (`human` | `service`, `service` iff issuer is
`local:service`) so service rows never pollute the human-audit columns. Service
rows carry a credential status badge (`active` / `expired` / `revoked` / `no
expiry` / `no credential`), because revoked machine identities are retained for
audit rather than deleted. Deactivated humans remain visible with an `inactive`
badge. Read-only except a per-row "Manage memberships" affordance: humans link into the applicable
S17 organization detail (a single link for one org, a dropdown of orgs for
several); service rows show none (S17 excludes them). `Alert` at top: "Admins are

rendered read-only inline via the per-row `siteAdmin` flag (no separate settings
endpoint needed).

**Data.** `GET /api/admin/users?page=&includeService=` (**built** —
`AdminUsersResource`). Returns `users, page, pageSize, total`; each user contains
`id, iss, sub, email, displayName, principalType, siteAdmin, lastLoginAt,
createdAt, deactivatedAt, credentialStatus,
organizations[{name, displayName, role}]`, admin-only.

**Acceptance.** A freshly-signed-in user appears; copyable `<iss>:<sub>` matches
the env format; a service account appears under the Service accounts filter with
`principalType=service` and no last login.

### S13 · Admin — Service tokens — `/console/admin/tokens`

**Purpose.** CI/CD credentials (the non-OIDC token kind).

**Access and navigation.** Org owners manage service tokens for orgs where their
live role is `owner`; site admins manage every org. The `Manage` sidebar group
shows only this entry to owners and the full management set to site admins.
Ordinary members cannot navigate to or call the inventory endpoint.

**Layout.** `DataTable`: description + short stable credential id + access profile | org | status | created by | created |
expires | last used | revoke. `Active / Inactive / All` `ToggleGroup`, default
Active; Inactive includes expired and revoked rows. Active rows sort by soonest
expiry. More than seven days is a normal timestamp, seven days or less is amber,
and past expiry is red. Revoked rows remain available for audit and show who
revoked them and when. Client pagination is 50 rows with description/org search;
server pagination is deferred.

"Mint service token" `Dialog` `Form`: description required (duplicates allowed
for zero-downtime rotation; warn when an active duplicate exists), convention
hint "one per service — e.g. github-actions/deploy", org `Select`, and mandatory
expiry `Select` (30/90/365 days, default 90). Only those three expiry values are
accepted server-side. Prefer the shell's selected manageable org, otherwise the
sole manageable org; a site admin with several orgs must select explicitly.
The form repeats the org scope and has an unchecked "Allow this token to create
and delete stacks" checkbox. The default `deploy` profile operates existing
stacks; the immutable `stack-lifecycle` profile adds exactly create/delete for
migrations and bootstrap, not rename/retag/org administration. Success uses S9's
shared one-time-token `Dialog`: raw value in memory only, copy feedback, and
"I've copied it." The value never enters a URL, storage, analytics, or logs.

**Lifecycle and audit.** Minting creates one `local:service` machine user, one
`service` membership, and one org-pinned `kind=service_account` credential.
The credential stores immutable `access_profile = deploy|stack_lifecycle`; changing it means
minting a replacement and revoking the old credential rather than silently changing a deployed
secret.
`api_tokens.created_by_user_id` records the console actor. Revocation is
idempotent soft revocation: set token `revoked_at` / `revoked_by_user_id` and
user `deactivated_at` / `deactivated_by_user_id` in one transaction. Never
reactivate an old secret; rotate by minting a replacement, updating CI, then
revoking the old account. Human and machine identities are not hard-deleted by
application APIs; a future human removal is deactivation. Service-token audit
rows are exempt from the 30-day expired-personal-token purge and retained
indefinitely for now.
Names are reusable display labels, never identifiers. Update activity carries the stable machine
user id plus exact token id and marks revoked actors, so overlapping or later same-name rotations
remain distinguishable.

Revocation rejects subsequent `Authorization: token ...` authentication
immediately. It does not implicitly cancel an update that already exchanged the
credential for an update lease; the confirmation points operators to Operations
→ Force unlock when deliberate interruption is required.

**Data.** Authorization-filtered `GET
/api/service-accounts?status=active|inactive|all` returns owned orgs for owners
and all orgs for site admins. Mutations stay tenant-explicit: `POST
/api/orgs/{org}/service-accounts` and idempotent soft revoke via `DELETE
/api/orgs/{org}/service-accounts/{id}`. Do not mix this inventory into personal
`GET /api/tokens` or add a site-admin-only tokens API.

**Acceptance.** Minted raw value is shown exactly once, authenticates `pulumi
login`, and can deploy an existing stack in its selected org; a stack-lifecycle
credential can additionally create/delete stacks but is worth
nothing outside it. Unsupported/missing expiry is rejected. Revocation
preserves creator/revoker/account history and causes new CLI token
authentication to 401; an already-issued update lease may finish. Owners see
only owned-org credentials, site admins see all, and ordinary members receive
403.

### S14 · Admin — Operations — `/console/admin/operations`

**Purpose.** One page for "why is something stuck": live locks and the
compaction work queue. Replaces psql spelunking.

**Layout.** Two stacked `Card`s, each polling every 5 seconds:

1. **Active locks** — live rows only (`expires_at > now()`): stack (link) |
   locked by (resolved human/service identity with opaque fallback) | acquired |
   expires (countdown) | update/preview (link) | force-unlock (destructive,
   `AlertDialog`). The dialog shows holder, acquired time, and last heartbeat.
   It explains that force-unlock cancels the update and the running Pulumi
   process will fail on its next request. Empty: "No stacks are locked."
2. **Compaction** — all active jobs first (oldest first), then the 50 most
   recent terminal jobs (newest first): stack | status badge | attempts | queued
   | started/completed | error message (truncated, tooltip). A retrying pending
   job labels its error as "Last attempt". Per-stack "Compact now" lives on S7;
   here is queue visibility only.

**Data.** `GET /api/admin/locks`, `GET /api/admin/compaction-jobs`, and guarded
`DELETE /api/admin/stacks/{org}/{project}/{stack}/lock?lockId={displayedLockId}`.
The delete returns 409 if the displayed lease has already gone or been replaced;
on success it atomically deletes that lock, cancels its in-progress update, and
clears the stack's active-update pointer. There is no event-retention card until
retention configuration and last-vacuum data have a real owner and endpoint.
The site-wide inventory reads require the site-admin allowlist; the two
stack-scoped mutations retain Cedar `stack:Unlock` and `compaction:Trigger`
authorization so future resource-scoped grants do not require another API
redesign.

**Acceptance.** A live lock created by a hung `pulumi up` is visible and safely
force-unlockable without risking a replacement lease; a failed compaction job
surfaces its error message.

### S17 · Org — Members & sharing — `/console/admin/orgs/{org}`

**Purpose.** The single home for "who belongs to this org, at what role, and what
have they been granted." Membership is what gates a principal's *access* to the
org's stacks — resolved per request, never baked into a token (see the remove-copy
below). This is the S11-successor for everything member/share related; S11 keeps
only tenant lifecycle.

**Who operates it.** Org `owner`s (their own org) and site admins (any org).
Authorized by a new owner-only Cedar action `org:ManageMembers`
(`appliesTo { resource: [Org] }`, added to `owner.cedar` next to
`serviceaccount:*`) plus `admin.cedar`'s unconstrained permit; loaded by the
existing `OrgEntityLoader`, role resolved by `PrincipalRoleResolver`. Precedent:
`serviceaccount:Create` already lets an owner write an `org_members` row (role
`service`) with no site-admin involved — human membership is the same shape.
Despite its `/console/admin/...` pathname, this detail route is deliberately
**outside** the site-admin-only route wrapper: an owner who is not a site admin
must reach it. On `/console/{org}`, an eligible owner sees a "Manage members"
action; a site admin can use the same action after selecting any org in the
all-orgs switcher, or follow the members-count link from S11. A site admin needs
no membership in the org — `admin.cedar` authorizes regardless. A non-owner
member who deep-links the detail route is returned to `/console/{org}`; the API
remains the server-authoritative authorization boundary.

**Layout.** Standalone organization detail page. `/console/{org}` stays focused
on stack browsing and supplies the owner/admin-only entry action; there is no
Stacks/Members tab shell.

- Members `DataTable` — **humans only** (`role IN ('owner','member','viewer',
  'guest')`): user (Avatar + email/name) | role `Select` inline
  (owner/member/viewer/guest) | granted stacks (guest rows: count → expander) |
  joined | remove. **Service accounts never appear here** — they are wholly owned
  by S13 (`serviceaccount:*` mint/revoke). Surfacing them would duplicate that
  function and render a row with no meaningful action (you can't demote a service
  account to viewer).
- **"Add member"** `Dialog`: user `Command` combobox (search existing users by
  email) + role `Select`. Choosing `guest` onboards a contractor to the
  additive-only tier (stack-sharing.md §4) — a bare guest sees nothing until
  granted a stack on S7.
- **Per-member guest grants** (read-only here): expanding a `guest` row lists that
  member's `policy_grants` (stack, template — read / read+secrets / write,
  created). This is the S17-side of stack-sharing.md §7, **visibility only** —
  grants are *minted* on the stack's Settings → Sharing card (S7), which owns
  `stack:ManageShares`. Whether a revoke affordance also lives here (a grant
  delete is one `policy_grants` row and closes the 404 gate immediately, §4) is an
  S7/§7-slice decision.
- **Remove member** → `AlertDialog` stating the real mechanism: *"Revokes their
  access to every stack in {org} on their next CLI request. Their login token
  stays valid for any other org they belong to."* — **not** "invalidates their
  tokens." OIDC/CLI tokens are account-scoped (V010); membership is re-checked per
  request, so access dies at the next authz check while the credential lives.
- **Last-owner soft block** — the UI refuses to remove or demote an org's final
  `owner`, with an inline explanation. Recoverable by a site admin either way
  (all-orgs switcher + `admin.cedar`), but the guard stops an org from silently
  losing its only self-service administrator.

**Data.** **Built full-stack in Slice 29.5** — the backend ships with the screen
(this action resolves S11's old "membership has no owner" flag). New Cedar action
`org:ManageMembers` (schema.cedar + `owner.cedar`; `admin.cedar` already covers it
via its unconstrained permit), then `GET /api/orgs/{id}/members` (owner-or-admin)
and `POST/PATCH/DELETE /api/orgs/{id}/members` (add / change role / remove), all
`@Authorize(action = "org:ManageMembers", loader = OrgEntityLoader)`. The
last-owner block is a **server-side invariant**, not just the UI soft-block.
Guest-grant listing reads `policy_grants` for the org's members; minting stays on
S7's shares API (stack-sharing.md §7). User search for the combobox is served by
the existing owner-scoped `GET /api/orgs/{id}/members/candidates` (already
shipped) — S12's list is not involved.

**States.** Empty (org just minted, zero members): "No members yet — add the first
owner." Loading → table skeleton. Attempting to remove/demote the last owner →
blocked inline.

**Acceptance.** An owner who is not a site admin manages members of their own org
and cannot touch another org's; adding a user as `guest` then granting one stack
on S7 makes exactly that stack visible to them; a role change reflects on the row;
removing a member toasts the access-revocation consequence (not a token claim);
the final owner cannot be removed or demoted; service accounts do not appear.
