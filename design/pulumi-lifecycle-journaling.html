Pulumi's lifecycle & journal, the state-db way

You've run pulumi up. You've never seen the HTTP conversation behind it. This page is that conversation — what the CLI sends, what we store, and the exact class that owns each step.

The 10-second version A user points PULUMI_BACKEND_URL at us and keeps using pulumi up unchanged. During a run the CLI streams tiny journal deltas; we just append them. We rebuild the full state on read by replaying that journal. That's the whole trick.

The whole system in three layers

Read top-to-bottom. Each layer only knows about the one below it.

LAYER 1
WIRE

The CLI ⇄ HTTP protocol

Start a run, grab a lock, stream journal + events, complete, read back. JAX-RS resources in modules/pulumi-api. → walk it

LAYER 2
STORAGE

Append-only rows in Postgres

We never store "the state." We store the run (stack_updates), the deltas (journal_entries), and a head pointer (stack_state). → the log

LAYER 3
REBUILD

Replay folds deltas into a checkpoint

On GET /export (and in background compaction) we replay the journal over a base snapshot to produce a full DeploymentV3. → replay

02 Two streams — never confuse them

During a run the CLI sends two parallel streams. They look similar but serve opposite purposes, and the code treats them differently.

⬡ Journal  PATCH

→ journal_entries
  • Is the source of truth for state.
  • Ordered & serialized: takes stack_state FOR UPDATE.
  • Replayed to rebuild the checkpoint.
  • Append-only & idempotent on retry.

◷ Events  POST

→ update_events
  • Is human-facing progress only.
  • No ordering invariant: skips the lock.
  • Drives the console timeline & diffs.
  • Never touched by state reconstruction.
If you remember one thing Journal rebuilds state. Events render a timeline. Reaching for update_events to answer "what resources exist?" is the classic wrong turn.

03 Locks & leases

Pulumi's rule: one stack, one mutating run. We enforce it with a time-boxed lease.

Acquire = one atomic statement

HQL can't express ON CONFLICT, so this is a justified native query. A live lock fails the WHERE → empty RETURNING → 409. A crashed-CLI lock (expired) is stolen in place.

The token is a rotating bearer

We store only the token's hash and hand the plaintext to the CLI as Authorization: update-token <uuid>. Every renew_lease mints a new one, so a leaked token dies within one window.

INSERT INTO stack_locks (…, expires_at, max_expires_at)
VALUES (…, LEAST(now()+ttl, now()+maxLifetime), now()+maxLifetime)
ON CONFLICT (stack_id) DO UPDATE SET … = EXCLUDED.…
 WHERE stack_locks.expires_at < now()      -- only steal an EXPIRED lock
RETURNING id, expires_at;
Two TTLsTwo failure codes
expires_at — sliding, pushed by each renew.
max_expires_at — hard ceiling; even continuous renew can't pass it (acquire uses LEAST).		 401 — missing/malformed token ("you didn't authenticate").
409 — valid token but expired / wrong stack / wrong updateID ("your lease is gone").
▶Why we revalidate the lease inside the write transactionthe TOCTOU gap

Lease-scoped routes pass two checks, and both matter:

  1. LeaseTokenFilter runs first: validates the token, confirms path (org/project/stack) + updateID match the lease, stashes a LeaseContext.
  2. The handler re-reads it, and for writes JournalAppender:110 calls LeaseRevalidator.requireLive() inside the same transaction, after taking stack_state FOR UPDATE.
The gap it closes: between filter admission and the actual write, a concurrent /complete could delete the lock row. Without the in-transaction recheck, a slow PATCH could land journal entries past end_journal_seq and corrupt the boundary. Revalidating under the row lock means the completer either blocks behind us, or we find the lock already gone and throw. StackLockRenewer closes the same gap for renew with an expires_at > now() predicate.

04 The journal log — what a row holds

One PATCH carries a batch; one entry becomes one journal_entries row. The columns that matter (JournalEntry.java):

ColumnMeaning
wire_sequence_idPulumi's per-run entry number (resets every run).
sequence_idServer-assigned replay order = start_journal_seq + wire id.
kindDiscriminator 0–7 — decides how replay reads the row.
operation_idTies a Begin to its later Success/Failure.
payload (jsonb)Full entry body — e.g. the resource's state on a Success.
remove_* / delete_* / pending_replacement_*Index instructions for mutating base-snapshot resources during replay.
Append-only & idempotent We never update a row. A retried batch of already-stored entries is a no-op (diffed by wire_sequence_id). A duplicate wire-id with different contents → JournalSequenceConflictException → 409. Two unique constraints back it up: UNIQUE(update_id, wire_sequence_id) and UNIQUE(stack_id, sequence_id).

05 The 8 entry kinds

The kind discriminator is the heart of the replay reducer (one switch arm each in JournalReplayer.add(), pinned to Pulumi v3.242.0). Click a kind to expand what replay does.

▶0Beginan operation starts

Records an in-flight op in incompleteOps. If the payload carries full resource context (urn, type, a valid operation.type) it also writes a pending_operations row. If the op never resolves, it surfaces in deployment.pendingOperations — that's the crash-recovery hook.

▶1Successthe workhorse — a resource is now live

Appends payload.state as a new live resource and clears the matching pending op. Then applies any index instructions on the row: removeOld/removeNew (drop), deleteOld/deleteNew (mark for deletion), pendingReplacement* (flag). This is where most of an up's resources come from.

▶2Failurean operation failed

Clears the in-flight op. The resource simply never materializes in the output deployment.

▶3RefreshSuccessrefresh re-read a resource

Replace the base-snapshot resource at index removeOld with the freshly-read state (or drop it if state is null). Sets hasRefresh, which triggers dependency rebuilding at materialization (see replay).

▶4Outputsfinal outputs for a resource

Replace a resource's state with its final outputs — e.g. the stack resource's outputs stamped at the end of a run.

▶5Writewholesale base replacement

Overwrite the entire working base with payload.newSnapshot. Implemented and tested, but rare in practice (not seen in the workbench run).

▶6SecretsProviderset the secrets provider

Set or update secrets_providers on the deployment. Idempotent — a no-op if the incoming provider equals the current one.

▶7RebuiltBaseStatea checkpoint within a run

Materialize everything so far into a fresh base and clear all transient replay maps. A semantic marker inside a run — not DB compaction.

The classic onboarding bug removeOld=2 does not mean "journal row 2." It's index 2 into the base checkpoint's resources[] array, as the CLI saw it. These indexes point back at resources from a prior run's exported state.

06 The sequence-ID trick

The cleverest, most confusing piece. Worth reading twice.

The problem

Pulumi numbers entries from an atomic counter at creation time. But its resource workers run concurrently and share one journal channel — so entries can reach our server out of order, even across separate PATCHes. Store arrival order and replay is wrong.

The fix

Make the replay key a deterministic function of the wire id, not of arrival. The offset is fixed once per run, so ORDER BY sequence_id always rebuilds the CLI's intended order.

sequence_id = stack_updates.start_journal_seq + wire_sequence_id
                       └─ per-run offset, claimed once on the FIRST patch ─┘
FieldScopeAssigned by
wire_sequence_idPer run (resets each run)Pulumi CLI
sequence_idPer stack (monotonic forever)state-db server

The CLI never knows sequence_id exists. It only sends sequenceID (= our wire_sequence_id). Insertion order = arrival order; replay order = sequence_id.

▶How the offset is claimed & the head advancedthe two atomic moves

Claim (first PATCH only)

JournalAppender:114 runs UPDATE stack_updates SET start_journal_seq = <current journal_seq> WHERE id=? AND start_journal_seq IS NULL. One-shot; later PATCHes read it back.

Advance (every PATCH)

UPDATE stack_state SET journal_seq = GREATEST(journal_seq, offset+max+1). GREATEST guards against an earlier PATCH that already advanced past this batch (out-of-order arrival).

07 Replay — log back into a deployment

StackAssembler.assemble(stackId) is the read path — and the exact code compaction uses, which guarantees a compacted snapshot equals what /export would have returned.

1 · Base. Load snapshots.checkpoint if a base exists, else an empty deployment. Note baseSeq = compacted_from_journal_seq.

2 · Stream. journal_entries WHERE sequence_id > baseSeq ORDER BY sequence_id — a scalar projection, no entity hydration.

3 · Fold. Feed each row to JournalReplayer.add(). On an update boundary (the updateId changes) materialize the current deployment and use it as the next run's base — that's how each run sees the prior run's result.

4 · Materialize. generateDeployment() folds the maps into a DeploymentV3; if any refresh happened it rebuilds dependencies, un-dangles parents, and normalizes URN aliases.

The replayer is a faithful Java port of Pulumi's Go reducer — its maps mirror the Go names (toRemove, toReplaceInSnapshot, operationIDToIndex, incompleteOps). It also reports a deployment version (3/4) and a sorted features list (hooks, views, taint…).

The bricked-state risk Pulumi refuses a stack whose export fails its snapshot integrity check (dangling parents, unknown aliases, missing providers). So replay must emit JSON that passes Pulumi's own validator — that's why it bothers with dependency rebuilding and URN normalization. The integrity scenarios are tracked in design/pulumi-state-testing-roadmap.md.

08 Compaction — keeping replay cheap

Replay from sequence 0 forever would get slower forever. Compaction folds the journal into a fresh base so replay only touches the tail. It's async, off the request path.

/complete enqueues a job (queue coalesces → ≤1 per stack). CompactionWorker on a schedule:

① claim a job with FOR UPDATE SKIP LOCKED (multi-pod safe) → ② lock stack_state → ③ run the same StackAssembler.assemble() → ④ write a new snapshots row, repoint base_snapshot_id, reset the counter.

What it does NOT do yet It doesn't delete journal rows — export just skips entries at/below compacted_from_journal_seq. Reads stay fast but table size isn't bounded; journal pruning needs an explicit retention policy first (open product question). Failed jobs retry to max-attempts; stuck "running" jobs get reclaimed by reclaimStuckJobs().

09 Concurrency invariants

Everything mutating a stack serializes on one row — stack_state via FOR UPDATE. This table is why the system is correct under multiple pods.

OperationLocks (in order)Prevents
Journal appendstack_state → stack_locksOverlapping seq ranges; writing past a completed boundary.
Complete / cancelstack_state → stack_locksStamping end_journal_seq mid-PATCH.
Compactioncompaction_jobs → stack_stateSnapshotting mid-append; double-claim across pods.
Start updatestacksDuplicate insert on idempotency retry; version collisions.
Acquire lockstack_locksTwo CLIs holding one stack.
Importstacks → stack_stateImporting over a live run (guards on active_update_id).

Append and complete agree on the order stack_state → stack_locks, so they queue behind the same first row and can't deadlock.

▶Odd one out: POST /importno lease protocol

StackImporter doesn't run the lease handshake. The CLI POSTs the whole checkpoint and immediately polls an already-SUCCEEDED update — there's no cloud work between start and finish. So it protects the operation with row locks + an active_update_id guard instead of an update-token, then installs the deployment as a brand-new base snapshot and bumps the version.

11 Your first change

A path that builds intuition fast.

1 · See a real journal. Run pulumi up from workbench/pulumi against state-db, then SELECT kind, wire_sequence_id, sequence_id, resource_urn FROM journal_entries ORDER BY sequence_id. Map each row to the 8 kinds.

2 · Trace one PATCH. Breakpoint in JournalAppender.append(); watch start_journal_seq get claimed and sequence_id derived.

3 · Trace one export. Step StackAssembler.assemble() → JournalReplayer.add() for that stack; confirm it matches pulumi stack export.

4 · Read the tests. JournalAppenderTest, StackAssemblerTest, and the Recorded*ReplayTest fixtures replay captured real journals — the best executable spec.
