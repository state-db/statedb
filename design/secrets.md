# state-db: Service Secrets

Companion to [`architecture.md`](./architecture.md), [`auth.md`](./auth.md), and [`db-schema.md`](./db-schema.md). The architecture doc establishes that state-db can act as a secrets provider for stacks that pick `type=service`; this doc fills in:

- how the Pulumi CLI's `serviceCrypter` interacts with our `/encrypt`, `/decrypt`, and `/batch-decrypt` endpoints,
- where the keyset material lives and how it is seeded,
- the cryptographic library and primitive used to satisfy the endpoints,
- the boundaries between service-managed secrets and external secrets providers (passphrase, AWS KMS, Azure Key Vault, GCP KMS, Vault).

---

## Goals

- **One provider out of many.** `type=service` is a sibling of `passphrase` / `awskms` / `azurekeyvault` / `gcpkms` / `hashivault`. state-db implements the service provider only; external providers run entirely client-side and are transparent to us.
- **Cross-stack isolation.** Ciphertext produced for stack A must not decrypt under a request scoped to stack B, even though both stacks share the same process and the same keyset.
- **Rename- and recreate-safe.** Renaming a stack must not orphan its ciphertext. Deleting and recreating a stack with the same name must not share authenticated context with the original.
- **Protection against checkpoint and journal exposure.** A leaked checkpoint JSON, journal-entry export, or partial DB dump (without the keyset row) must not reveal plaintext. This is the boundary the service provider buys you. It is *not* protection against a full DB compromise — see "Threat model" below.
- **No operator-managed key files.** The keyset is generated by the service on first boot and stored in Postgres. Self-hosting must not require operators to handle key files, environment-variable secrets, or rotation rituals in Wave 1.
- **No hand-rolled crypto.** All cryptographic operations go through [Google Tink](https://developers.google.com/tink) (`com.google.crypto.tink:tink`). We do not derive keys, manage nonces, define envelope framing, or implement constant-time comparisons ourselves.

## Non-goals

- **Keyset rotation.** Wave 1 ships a single-key keyset, seeded once. Tink keysets natively support multi-key rotation (primary-for-encrypt, any-for-decrypt) when we need it.
- **KMS-wrapped keyset.** Operators who want the keyset wrapped by an external KMS should use one of the external providers directly (`pulumi stack init --secrets-provider=awskms://...`) — the service provider exists for the simple self-hosted case. Tink supports KEK-wrapped keysets natively if we ever want to add it.
- **At-rest encryption of Postgres.** That is the operator's responsibility, as already stated for OIDC client secrets and tokens in [`architecture.md`](./architecture.md). The keyset joins that list.
- **Per-resource ACLs on `/encrypt` / `/decrypt`.** Any principal allowed to update a stack is allowed to encrypt/decrypt for that stack. The endpoints are token-authenticated and stack-scoped through the standard tenant resolver; they are *not* lease-protected.

## How Pulumi's CLI uses these endpoints

Each Pulumi stack carries a `secretsProvider` declaration that selects the crypter. The CLI dispatches on `secretsProvider.type`:

| Provider type | Crypter | Backend interaction |
|---------------|---------|---------------------|
| `service` | `serviceCrypter` | Calls `/encrypt`, `/decrypt`, `/batch-decrypt` on the backend |
| `passphrase` | `symmetricCrypter` | All crypto local; backend stores opaque ciphertext |
| `awskms`, `azurekeyvault`, `gcpkms`, `hashivault` | `cloudCrypter` | All crypto local against the named KMS; backend stores opaque ciphertext |

The provider choice is persisted in two places that the CLI keeps in sync:

- The stack config file on the user's machine (`Pulumi.<stack>.yaml`), used by the CLI to pick a crypter before talking to the backend.
- The stack's deployment journal as a `SecretsManager` entry carrying `{type, state}`. `state` for `service` is `{owner, project, stack, url}`.

The deployment record is what makes the stack self-describing across machines and CI runners.

### Switching providers

`pulumi stack change-secrets-provider <target>` decrypts every secret in the stack under the current provider, re-encrypts under the target provider, and writes a fresh `SecretsManager` journal entry plus `write`-kind entries carrying the re-encrypted payloads. From state-db's perspective this is an ordinary update — no provider-specific logic is needed in the backend beyond serving `/encrypt` and `/decrypt` when the *current* provider is `service`.

A consequence: when a stack is in service mode, our derived key protects its secrets. When the stack switches *away*, those secrets are gone (re-encrypted under the new provider). If the stack switches *back* later, the same derived key reappears for the new run's secrets. No history needs to be tracked.

### Where plaintext is and isn't

| Path | Plaintext visible to state-db? |
|------|-------------------------------|
| `service` provider, `/encrypt` request | Yes — intrinsic. HTTPS at the deployment boundary is assumed. |
| `service` provider, `/decrypt` response | Yes — intrinsic. |
| `service` provider, journal/checkpoint payloads | No — payload bytes are ciphertext we produced. |
| Any external provider | No, anywhere — the backend only sees ciphertext blobs inside payloads. |

An exposure of `journal_entries` / `snapshots` / `update_events` *without* `service_secrets_keyset` (a partial dump, a leaked backup of a subset of tables, log payloads) does not reveal plaintext for any provider. A compromise that includes `service_secrets_keyset` reveals plaintext for `service`-provider stacks and the GitHub App credentials in `vcs_app_registrations` — external providers remain protected by their respective KMS.

The GitHub App private key and OAuth client secret use this keyset with `vcs-app:<host>[:oauth]:<version>` as associated data. That string's ninth byte starts the host, so it is ASCII or a UTF-8 lead byte, never a UUIDv7 variant byte (`0x80`–`0xBF`). Neither use can decrypt the other's ciphertext.

## Keyset material

A single serialized Tink keyset lives in Postgres in the `service_secrets_keyset` table:

```sql
CREATE TABLE service_secrets_keyset (
    id            SMALLINT PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    key_material  BYTEA    NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`key_material` holds the bytes returned by `TinkProtoKeysetFormat.serializeKeyset(handle, InsecureSecretKeyAccess.get())` for a freshly generated `AES256_GCM` keyset. The `CHECK (id = 1)` constraint enforces singleton at the DB layer. The contents are opaque to state-db beyond "feed this back to Tink at startup"; Tink owns the framing and may evolve it across versions.

### Bootstrap seeding

The row is seeded by `BootstrapProvisioner`, not by Flyway. Flyway migrations should be deterministic across environments and reproducible from a snapshot; generating random key material inside a migration violates both. The bootstrap path uses the existing `AdvisoryLock#runExclusive` pattern documented in `AGENTS.md`:

1. Bootstrap acquires `AdvisoryLock.SECRETS_KEYSET_BOOTSTRAP_LOCK`.
2. Inside the lock, the provisioner checks for the singleton row. If absent, it calls `KeysetHandle.generateNew(PredefinedAeadParameters.AES256_GCM)`, serializes the handle, and inserts the bytes as a bind parameter:
   `INSERT INTO service_secrets_keyset (id, key_material) VALUES (1, ?) ON CONFLICT (id) DO NOTHING;`.
3. Releases the lock.

Generating the keyset in-process keeps entropy under Tink's control (which uses `SecureRandom` internally) and means a SQL audit log capturing the literal `INSERT` does not record key bytes inline — the value travels as a bound parameter.

Concurrent pods serialize through the advisory lock; followers find the row already inserted and no-op. A crashed leader releases the lock when its DB session is reaped.

### Keyset access at runtime

`SecretsAeadHolder` is `@Startup`-scoped, reads the singleton row once, calls `TinkProtoKeysetFormat.parseKeyset(bytes, InsecureSecretKeyAccess.get())`, and obtains an `Aead` primitive via `handle.getPrimitive(RegistryConfiguration.get(), Aead.class)`. The `Aead` is the only object the rest of the service interacts with — the keyset bytes never leave the holder.

The holder never logs the key material. The bytes never appear in env vars, deployment manifests, or `ps` output — the only place they exist is in the DB row and in process memory.

If the singleton row is missing at startup (a bootstrap regression), `SecretsAeadHolder` fails-fast rather than auto-generating outside the locked path. Silent auto-generation in unexpected places is exactly the bug that would silently rekey a deployment after a partial DB restore.

### Why DB-resident and not env-supplied

- **Zero operator burden.** Self-hosters don't need to generate a key, persist it across deploys, or rotate environment variables. The service is opinionated about boot.
- **Consistent with existing posture.** OIDC client secrets and OIDC session-encryption secrets are already required to be present (DB-stored or env-supplied). At-rest DB encryption is already documented as the operator's responsibility (`architecture.md`). The keyset joins that list, not a new one.
- **No drift across pods.** Two pods reading from the DB cannot disagree about the key. Two pods reading from env can, if the env is rolled inconsistently.

The tradeoff is real and worth naming directly: **co-locating the keyset row with the ciphertext means a full DB compromise reveals every service-provider stack's plaintext.** The protection the service provider buys you is against checkpoint and journal *exposure paths short of full DB access* — leaked exports, backup snapshots delivered to the wrong audience, log scrapers harvesting payload bytes, partial dumps of `journal_entries` or `snapshots` shared during debugging. Any of those leaks ciphertext but not the keyset row, and ciphertext alone is unintelligible.

Operators whose threat model includes a full DB compromise should not rely on the service provider. The right answer for that threat model is one of the external providers (`awskms`, `azurekeyvault`, `gcpkms`, `hashivault`), where the encryption key lives in an external KMS and the database holds only opaque ciphertext. The deployment guide must say this plainly.

## Encryption

All cryptographic operations are delegated to Tink's `Aead` primitive, configured with `AES256_GCM`. We do not derive keys, manage nonces, define envelope framing, or perform any constant-time comparisons ourselves — those are Tink's responsibilities.

### Cross-stack isolation via AAD

Each `/encrypt` and `/decrypt` request resolves the stack through `StackRefResolver` (tenant-isolated, same path resolution every authenticated stack route uses) and obtains the immutable `stack.id` (UUIDv7, 16 bytes). Those 16 bytes are passed as the **associated data** to every `Aead.encrypt` and `Aead.decrypt` call:

```java
byte[] ciphertext = aead.encrypt(plaintext.getBytes(UTF_8), stackIdBytes);
byte[] plaintext  = aead.decrypt(ciphertext, stackIdBytes);
```

AES-GCM authenticates the AAD as part of the tag. A ciphertext produced under stack A's AAD presented to a decrypt with stack B's AAD fails the tag check unconditionally — that is the cryptographic guarantee GCM is built to provide. Cross-stack isolation falls out of this without any per-stack key derivation.

Binding to `stack.id` (UUIDv7), rather than the wire `(owner, project, name)` tuple or the `url`:

- Survives stack renames. The UUID is stable across `pulumi stack rename`.
- Forbids reuse across delete-and-recreate cycles. A new stack with the same name gets a fresh UUID; old ciphertext fails AAD authentication against it.
- Ignores URL. The wire `secretsProvider.state` carries `url` for Pulumi's bookkeeping, but tying decryption to it would break on operator-side DNS renames, reverse-proxy rearrangements, and instance migrations — none of which should orphan a stack's secrets.

### Wire format

Tink's `Aead` returns opaque bytes whose framing is Tink's internal concern (a key-ID prefix followed by nonce, ciphertext, and tag). We do not inspect, parse, or reframe those bytes.

Pulumi's `serviceCrypter` round-trips the ciphertext through standard base64 — confirmed against `pulumi/pulumi` at tag `v3.242.0`:

- `pkg/secrets/service/manager.go` [L67-L72](https://github.com/pulumi/pulumi/blob/v3.242.0/pkg/secrets/service/manager.go#L67-L72), [L94-L100](https://github.com/pulumi/pulumi/blob/v3.242.0/pkg/secrets/service/manager.go#L94-L100), [L107-L124](https://github.com/pulumi/pulumi/blob/v3.242.0/pkg/secrets/service/manager.go#L107-L124).
- `sdk/go/common/apitype/stacks.go` [L79-L130](https://github.com/pulumi/pulumi/blob/v3.242.0/sdk/go/common/apitype/stacks.go#L79-L130) — request/response DTOs use `[]byte` / `[][]byte`, which Go's `encoding/json` encodes as RFC 4648 §4 standard base64 with padding.

So our handlers base64-encode the bytes Tink returns and base64-decode the bytes the CLI sends, with no other transformation. We emit standard base64 (not `base64url`) and add no textual prefix.

### Rotation

Tink keysets natively support multiple keys with one marked primary. Encrypt uses the primary; decrypt tries all keys in the keyset until one succeeds (matched by the key-ID prefix Tink embeds in the ciphertext). Wave 1 ships a single-key keyset and does not exercise rotation; adding a new primary later is `keysetManager.add(...).setPrimary(...)` plus a re-serialize-and-store under the same advisory lock. Old ciphertexts continue to decrypt without re-encryption.

## Endpoints

All three endpoints are mounted under the standard tenant-scoped stack path. Authentication is the project's existing token filter; the stack is resolved through `StackRefResolver` before any crypto runs. None of them participate in update leasing.

### `POST /api/stacks/{org}/{project}/{stack}/encrypt`

```
request : {"plaintext": "<utf-8 string>"}
response: {"ciphertext": "<base64 envelope>"}
```

Identical plaintexts encrypted twice produce distinct ciphertexts — the random nonce guarantees this and Pulumi expects it. No memoization.

### `POST /api/stacks/{org}/{project}/{stack}/decrypt`

```
request : {"ciphertext": "<base64 envelope>"}
response: {"plaintext":  "<utf-8 string>"}
```

Errors return HTTP 400 with a generic body (`{"code":400,"message":"invalid ciphertext"}`) for any of: unparseable base64, unknown version byte, truncated payload, GCM tag failure. The error does not leak which check failed.

### `POST /api/stacks/{org}/{project}/{stack}/batch-decrypt`

```
request : {"ciphertexts": ["<env>", "<env>", ...]}
response: {"plaintexts":  {"<env>": "<plaintext>", ...}}
```

The response is a *map* keyed by the input ciphertext, which naturally deduplicates: an input list containing the same ciphertext twice yields one entry. Order is not preserved (and the CLI does not require it).

Failure policy is fail-the-whole-batch: any single invalid entry causes the entire request to return HTTP 400. Pulumi Cloud behaves the same way, the recorder does not exercise partial-failure, and a mixed map would force the CLI to handle a code path it does not have.

## Threat model

| Attacker has… | Can read service secrets? | Mitigation |
|---------------|--------------------------|------------|
| Network access between CLI and state-db | No | TLS at the deployment boundary (operator responsibility) |
| Leaked checkpoint export, journal-entry dump, or event-log payload — ciphertext only | No | Payloads are AES-GCM ciphertext; without the keyset row, decryption is computationally infeasible |
| Backup snapshot of a *subset* of tables that does not include `service_secrets_keyset` | No | Same as above — ciphertext alone is unintelligible |
| Read-only snapshot of the *full* DB, including `service_secrets_keyset` | **Yes** | Operator must protect the DB with at-rest encryption and access controls; for stronger separation, use an external secrets provider |
| Process memory at runtime | Yes (the live Tink keyset and any in-flight plaintext) | Standard JVM hardening; nothing crypto-specific helps here |
| One stack's compromised CLI token | Only that stack's secrets | `stack.id` is the AAD; AES-GCM fails the tag on cross-stack decrypt |
| Replay of an old ciphertext into a recreated stack with the same name | No | Recreated stack has a fresh UUID, so a fresh AAD; old ciphertext fails the tag |

The "full DB snapshot" row is the boundary of what the service provider protects. External secrets providers eliminate that row entirely: state-db never sees plaintext or key material, so a full DB compromise leaks only opaque ciphertext that requires the external KMS to decrypt. The tradeoff is that operators must run and pay for that KMS.

## Tests

We do not test Tink — Google does that. Our tests cover the wiring between the endpoints, the resolver, the AAD binding, and the keyset bootstrap.

Unit tests (no DB, crypter constructed with an in-memory Tink keyset):

- Round-trip for ASCII, UTF-8, empty string, and binary-looking-but-string content.
- Two encrypts of the same plaintext yield distinct ciphertexts (Tink's nonce is random).
- Tampering: flipping any single byte of the base64 → decrypt 400.
- Wrong-stack: ciphertext produced with stack-id A as AAD, decrypted with stack-id B as AAD → 400.
- Unparseable base64 → 400.

Integration tests (full app + DB + bootstrap):

- Bootstrap seeds exactly one row; second boot is idempotent under the advisory lock.
- `/encrypt` then `/decrypt` round-trips under the same stack path.
- `/encrypt` then `/decrypt` under a *different* stack path returns 400.
- `/batch-decrypt` deduplicates repeated input ciphertexts.
- `/batch-decrypt` with one bad entry → whole batch 400.

Fixture replay (`tools/pulumi/recorder/fixtures/.../encrypt|batch-decrypt`):

- Recorder fixtures use redacted `[secret]` placeholders, so replay asserts HTTP shape and status only — actual crypto behavior is covered by the unit and integration tests above. This split is intentional and the test code should be explicit about it.

## Future work

- **Keyset rotation.** Add a second key to the Tink keyset and mark it primary under the same advisory lock. Old ciphertexts continue to decrypt under the previous key via Tink's key-ID prefix; no envelope change, no rekey-on-read job required for correctness.
- **KMS-wrapped keyset.** Tink supports `KeysetHandle.read(reader, kekAead)` for storing the keyset wrapped under a KEK (AWS KMS, GCP KMS, etc.). Operators with an external KMS could opt into this without switching individual stacks to a delegated provider.
- **Audit log of decrypt requests.** Per-stack metrics or an audit table for `/decrypt` and `/batch-decrypt`. Useful but distinct from this slice.
